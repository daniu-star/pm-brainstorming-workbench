# Loop Engineering Product

把「一个人问、一堆 agent 答」升级为「一支研发团队按固定工艺交付」。
核心不是让模型写得更多，而是让**每一轮都留下可复现的证据、可评分的结论、可回退的改动**。

## 何时使用

- 产品要发版/交付，需要一次「产品 + 工程 + 质量」联合体检；
- 拿到 PRD 或验收矩阵，需要逐条核对「真做了没有」；
- MVP 原型要打磨到可演示，需要连续多轮「测试 → 反馈 → 优化 → 评测」；
- 已有 Loop 机制（如 QA Loop）想沉淀成可复用的组织流程。

不适用：单文件小改动、纯文档写作、无自动化测试且无运行环境的仓库（此时先补「可验证性」再加 Loop）。

## 五段闭环（Loop 一次 = 一轮）

```
规划 PLAN ──▶ 研发 BUILD ──▶ 测试 TEST ──▶ 迭代 ITERATE ──▶ 评测 EVALUATE
   ▲                                                            │
   └──────────────── 未达阈值 且 轮次未耗尽 ◀───────────────────┘
                     达阈值 / 轮次耗尽 ──▶ 交付 DELIVER
```

- **PLAN**：产品组把需求收敛成「本轮目标 + 验收口径 + 风险清单」，写进 round scope，禁止边做边改目标。
- **BUILD**：客户端/服务端/发布运维按各自写权限并行修复；测试组同步补回归用例。
- **TEST**：测试组**真跑**命令（后端全量、前端类型检查/单测/构建/e2e），真实输出即证据。
- **ITERATE**：把「未通过项」变成下一轮的最小改动集，按 P0→P1→P2 排序，一次只改必要范围。
- **EVALUATE**：评测组独立打分，**必须先自证一条命令**，再按 8 维评分卡给分并写清扣分理由。

## 团队编制（7 角色，可按仓库补充）

| 角色 | 职责 | 写权限 |
|---|---|---|
| 产品组 | 需求→验收口径、流程可走通性、范围蔓延 | `docs/**`（仅规格增量） |
| 设计体验组 | 交互状态机（空态/加载/错误/恢复）、可访问性、文案 | 只读 |
| 客户端开发组 | 前端逻辑、竞态、版本单调、SSE 解析 | `frontend/**` |
| 服务端开发组 | 幂等、状态机、租约、事务边界、错误码 | `backend/**` |
| 测试组 | 真跑验证、补边界/回归用例、flake 记录 | `backend/tests/**`、`frontend/tests/**` |
| 评测组 | 独立打分、硬上限裁定、证据核对 | 只读 |
| 发布运维组 | CI、启动脚本、健康检查、回滚与可观测 | `scripts/**`、`.github/**`、`docs/**` |

写权限**硬隔离**：一个角色不得跨侧改动；跨侧需求写进 findings 交给对应角色。

## 8 维评分卡（满分 100）

| 维度 | 权重 | 关注点 |
|---|---|---|
| 产品与需求达成 | 20 | FR/AC 覆盖、主流程可走通、范围与用户价值 |
| 功能正确性 | 15 | 主路径/边界/异常路径的真实行为 |
| 数据一致性与状态机 | 15 | 并发、幂等、版本单调、事务原子性 |
| 交互与前端逻辑 | 15 | 竞态、去重、加载/错误/恢复、深链与刷新 |
| 架构与代码质量 | 10 | 分层、契约单一真相、可读性与演进成本 |
| 安全与错误处理 | 10 | 越权、泄漏、错误码语义、密钥与输入校验 |
| 自动化测试与证据 | 10 | 覆盖真实行为、跨进程/崩溃注入、无弱化绿 |
| 文档与可运维 | 5 | 命令可复现、部署/回滚/已知边界 |

**硬规则（不可谈判）**

1. 存在未修 P0 → 总分上限 **70**；存在 ≥3 条未修 P1 → 上限 **85**。
2. 削弱测试（删用例、改期望值、`skip`、`assertTrue(True)`）换来的绿 → 上限 **60** 且必须回退。
3. 评分必须引用真实命令输出（如 `Ran 577 tests / OK`），推演与「应该没问题」不算证据。
4. 同一缺陷跨轮重复出现且无进展 → 评测组必须降分并写「僵局原因」。

## 退出条件

- `score >= target`（默认 95）→ 交付；
- 轮次用尽（默认 5）→ 交卷，输出「未闭合项 + 最小下一步」，**不允许把未完成说成完成**。

## 使用方法

1. 复制 `scripts/loop-workflow.js` 到目标仓库（或 `scripts/loops/`），按 `args` 覆盖仓库路径与命令。
2. 用 workflow 工具执行：

```
workflow({
  meta: { name: "loop-engineering-product", description: "五段闭环产品研发 Loop" },
  args: { repoPath: "<abs repo>", maxRounds: 5, target: 95, focus: "" },
  script: <scripts/loop-workflow.js 的内容>,
  run_in_background: true
})
```

3. 每轮结束看 `rounds[i].score` 与 `rounds[i].retest`；收尾看 `releases` 建议与 `openItems`。
4. 结果归档：`docs/loop-runs/round-N.md` + 汇总 `docs/loop-runs/README.md`（模板见 `assets/report-template.md`）。
