# 轮次协议与证据纪律（Loop Engineering Product v1.0）

## 一轮的固定时序

```
1. PLAN    产品组产出本轮 scope（目标 / 验收口径 / 非目标 / 风险）        —— 1 次 agent
2. AUDIT   产品组 + 设计体验组 + 客户端组 + 服务端组 + 测试组 并行只读审计  —— 5 次并行
3. SCORE   评测组评分（先跑一条命令自证，再按 8 维打分 + 硬上限）          —— 1 次 agent
4. GATE    score >= target 或轮次耗尽 → 输出；否则继续
5. FIX     客户端修复 + 服务端修复 并行；测试组补回归用例；发布组按需     —— 2~3 次并行
6. RETEST  测试组真跑全量命令，产出真实数字与失败清单                      —— 1 次 agent
7. RECORD  落盘 docs/loop-runs/round-N.md，进入下一轮
```

预算参考：每轮 9~11 次 agent 调用；5 轮约 45~55 次。可在 `maxRounds` 收敛。

## 发现项格式（findings）

```json
{
  "id": "C-01",
  "area": "frontend | backend | product | ux | test | docs",
  "severity": "P0 | P1 | P2",
  "title": "一句话说清缺陷",
  "evidence": "文件:行号 或 接口 + 复现步骤",
  "impact": "用户/数据会受到什么影响",
  "fix": "最小修法（可执行）",
  "verify": "修复后如何验证（命令或用例名）"
}
```

严重度定义

| 级别 | 定义 | 处理时限 |
|---|---|---|
| P0 | 主流程断裂、数据丢失/错写、越权泄漏、无法启动 | 本轮必修，否则不得出高分 |
| P1 | 关键状态缺口、错误不可恢复、无证据的「假通过」 | 3 条以内可接受降级发布 |
| P2 | 体验瑕疵、文案、非关键路径 | 可延后，需记录 |

## 证据纪律

1. **真实输出优先**：评审结论必须引用命令输出片段（`Ran 577 tests / OK`、`tsc exit 0`、HTTP 状态码 + body 片段）。
2. **禁止预填通过**：不能因为「代码里看起来有」就判定通过；必须有点击路径、接口调用或测试用例。
3. **不修改期望值**：修复缺陷不得改测试期望；确需变更契约时，先改文档与契约，再改两侧实现与测试。
4. **跨进程/崩溃类缺陷**：必须真起两个进程或用注入点，不能串行模拟冒充并发。
5. **记录不确定**：「未验证/环境不支持」如实写，不折中成「应该没问题」。

## 修复轮规则

- 一轮只改「评分清单 + 审计发现」里的项，禁止顺手重构。
- 最小改动：能改三行不改三十行；能补一个分支不重写模块。
- 每处改动必须自带验证（命令或新增用例名）。
- 修不了的写 `skipped` + 原因 + 建议（不要假装修好）。
- 跨侧依赖（前端要后端字段）写进 findings 交给对应角色，不越界提交。

## 僵局处理

- 同一缺陷连续 2 轮出现且无实质进展 → 评测组降分，并要求下一轮**只做这一件事**。
- 修复后复测仍失败 → 回滚该改动，改走「绕过 + 记录」并在报告中明示。
- 环境问题（端口占用、依赖缺失、网络不可达）不算产品缺陷，但必须写进发布清单的「已知行为」。

## 产物清单（每轮）

```
docs/loop-runs/
├── README.md            # 5 轮汇总：分数曲线、修复主线、未闭合项
├── round-1.md           # 本轮 scope、findings、score、fix、retest
├── round-2.md
└── round-N.md
```

每份 `round-N.md` 必含：本轮分数与 8 维明细、P0/P1/P2 清单、修复文件与验证命令、复测真实输出、下一轮计划。

## 交付判据（DELIVER）

- 后端全量测试通过且数字写入报告；
- 前端类型检查/单测/构建通过（有 e2e 则跑关键路径）；
- 无未修 P0；P1 有明确处置（修复或记录）；
- 启动脚本在干净环境可拉起（或写明缺失依赖）；
- 已知边界、回滚方式、未闭合项写入发布清单。
